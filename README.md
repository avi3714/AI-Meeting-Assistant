# MeetMind – AI Meeting Assistant

An AI-powered meeting assistant that converts meeting audio into speaker-attributed transcripts, structured summaries, and downloadable PDF reports.

MeetMind combines automatic speech recognition, speaker diarization, speaker recognition, and configurable large language model execution to simplify meeting documentation.

Users can generate AI-powered summaries through either a remotely hosted Ollama API or a locally installed Ollama instance.

# Application Features and Functionality

The AI Meeting Assistant provides an end-to-end workflow for converting meeting recordings into structured, speaker-attributed transcripts and AI-generated meeting reports.

## 1. Audio Upload and Meeting Processing

Users can upload meeting recordings in WAV, MP3, M4A, FLAC, or OGG format and initiate the processing workflow.

The backend performs the following stages:

1. Audio preprocessing using FFmpeg.
2. Speaker diarization using Pyannote Audio.
3. Speech transcription using Faster-Whisper.
4. Speaker matching using SpeechBrain ECAPA embeddings.
5. Transcript and diarization merging.
6. AI-powered meeting summarization using Ollama and Qwen 2.5.

## 2. Cosine Similarity Threshold Configuration

Users can adjust the cosine similarity threshold using the slider on the home screen.

- Available range: 0.60–0.80.
- Recommended default: 0.72.

Cosine similarity measures the similarity between two speaker embedding vectors generated by SpeechBrain.

The cosine similarity is calculated as:

\[
\text{Cosine Similarity}(A,B)=
\frac{A\cdot B}{\|A\|\|B\|}
\]

The threshold determines how strict the speaker-matching process should be:

- Higher threshold: Matching becomes stricter. A segment needs a higher similarity score to match an existing speaker.
- Lower threshold: Matching becomes more permissive. Segments with lower similarity scores may be assigned to an existing speaker.

For example, for a similarity score of 0.74:

| Threshold | Matching decision |
|---|---|
| 0.70 | Meets the threshold |
| 0.72 | Meets the threshold |
| 0.75 | Does not meet the threshold |

This is an illustrative example. A higher threshold does not necessarily guarantee better identification; it can also leave more segments unmatched.

## 3. Automatic Speaker Identification

The application uses two components.

**Speaker Diarization – Pyannote Audio**

Pyannote analyzes the recording and identifies portions of audio associated with different speakers. It produces labels such as `SPEAKER_00`, `SPEAKER_01`, and `SPEAKER_02`.

**Speaker Matching – SpeechBrain ECAPA**

SpeechBrain generates speaker embeddings and compares them to associate audio segments with speaker profiles. Segments that cannot be confidently assigned may be marked as `UNKNOWN` for manual correction.

## 4. Transcript Generation with Speaker Labels and Timestamps

The application combines transcription and diarization results to generate a structured transcript containing:

- Speaker identification labels.
- Start and end timestamps.
- Recognized spoken content.
- Separate segments for different portions of the conversation.

Example:

**SPEAKER_00**

`[6.22s – 11.24s]`

> Hey guys, good to have you all together. It's been a pleasure, good morning.

**UNKNOWN**

`[11.24s – 13.28s]`

> yeah,

**SPEAKER_01**

`[13.50s – 24.94s]`

> I think I'd start off talking about something that just randomly hit me today...

The interface visually distinguishes identified speakers from unknown speakers, making it easier to review the transcript.

## 5. Assign Names to Unknown Speakers

Automatic speaker identification may not confidently associate every segment with an existing speaker. Such segments are marked as `UNKNOWN`.

Users can manually assign these segments to detected speakers:

1. Locate a segment marked `UNKNOWN`.
2. Find the speaker assignment dropdown below the segment.
3. Select the appropriate detected speaker, such as `SPEAKER_00` or `SPEAKER_01`.
4. Repeat for other unknown segments.

The selected speaker assignment is incorporated when the updated transcript is generated. This allows users to correct uncertain assignments without processing the entire recording again.

## 6. Modify Existing Speaker Assignments

The application also allows users to correct speaker assignments that were automatically generated.

For example, a segment initially assigned to `SPEAKER_00` may actually belong to `SPEAKER_01`.

Users can correct it as follows:

1. Locate the transcript segment that needs correction.
2. Find the currently assigned speaker label.
3. Click the **Modify** option.
4. Select the correct speaker from the available dropdown.

The segment will then be assigned to the selected speaker when the updated transcript is generated.

## 7. Regenerate the Transcript

After assigning unknown segments and correcting existing speaker assignments, users can regenerate the transcript.

The updated transcript incorporates the user's corrections, including:

- Replacing `UNKNOWN` assignments with detected speakers.
- Correcting incorrectly assigned speaker labels.
- Applying updated speaker information to the transcript.
- Generating an updated transcript report.

The original processing results are preserved while the manual corrections are applied to the updated report.

**Important:** Regenerating the transcript applies manual corrections. It does not require repeating the complete audio transcription and diarization pipeline.

## 8. Assign Participant Names

Users can enter actual participant names corresponding to detected speaker labels.

For example:

| Detected speaker | Participant name |
|---|---|
| SPEAKER_00 | Rahul |
| SPEAKER_01 | Avinash |
| SPEAKER_02 | Priya |

This replaces generic speaker labels with meaningful participant names in the updated reports.

## 9. Generate an Updated AI Meeting Summary

After reviewing speaker assignments and entering participant names, users can generate an updated meeting summary.

The application uses Ollama to run the Qwen 2.5 3B language model. The model can be accessed through either:

- A remotely hosted Ollama-compatible API.
- A locally running Ollama instance.

The corrected transcript is used as the basis for generating the updated summary.

The summary contains the following sections:

- **Executive Summary:** A concise overview of the meeting.
- **Topics Discussed:** Major subjects covered during the discussion.
- **Detailed Discussion:** A comprehensive account of the conversation.
- **Speaker-wise Contributions:** Contributions made by individual participants.
- **Key Takeaways:** Important points and insights.
- **Decisions and Agreements:** Decisions reached during the meeting.
- **Action Items:** Tasks and responsibilities identified.
- **Open Questions and Follow-ups:** Issues requiring further discussion or action.
- **Conclusion:** An overview of the meeting outcomes.

Using the corrected transcript helps ensure that the updated summary reflects the reviewed speaker identities and participant names.

## 10. PDF Report Generation

The application generates two main PDF reports.

**Meeting Transcript PDF**

Contains the generated transcript with timestamps and speaker identification information.

**Meeting Summary PDF**

Contains the structured AI-generated meeting summary, including key takeaways, decisions, action items, and speaker-wise contributions.

These reports can be downloaded, shared, and used for future reference.

# Complete Application Workflow

The complete user journey is as follows:

1. **Configure speaker matching:** Adjust the cosine similarity threshold or retain the recommended value of 0.72.
2. **Upload recording:** Select a meeting audio file in a supported format.
3. **Process recording:** Start the backend processing pipeline.
4. **Identify speakers:** Detect speakers and associate audio segments with speaker labels.
5. **Generate transcript:** Obtain a timestamped transcript containing speaker labels.
6. **Review unknown segments:** Assign `UNKNOWN` segments to the appropriate detected speakers.
7. **Modify speaker assignments:** Correct incorrectly identified speaker segments.
8. **Enter participant names:** Associate actual names with detected speaker labels.
9. **Regenerate transcript:** Generate an updated transcript incorporating manual corrections.
10. **Regenerate summary:** Generate an updated AI meeting summary using the corrected transcript.
11. **Download reports:** Obtain the final transcript and summary as PDF documents.

The workflow combines automated audio processing with human verification to produce more useful and understandable meeting documentation.

# Installation and Setup

The following instructions describe how to install and run MeetMind on Windows using PowerShell.

If you are using Linux or macOS, the equivalent installation commands may differ.

## 1. Clone the Repository

Open PowerShell or the VS Code terminal.

Navigate to the directory where you want to store the project.

Clone the repository:

```powershell
git clone https://github.com/avi3714/AI-Meeting-Assistant.git
```

Navigate into the project directory:

```powershell
cd AI-Meeting-Assistant
```

Open the project in Visual Studio Code if desired:

```powershell

```

After cloning, the project will contain the backend, frontend, scripts, and dependency files.

## 2. Install Python

MeetMind uses Python for audio processing, transcription, diarization, speaker recognition, and backend API operations.

Download Python 3.12 from:

https://www.python.org/ftp/python/3.12.10/python-3.12.10-amd64.exe

During installation:

1. Start the Python installer.
2. Enable **Add Python to PATH**.
3. Complete the installation.
4. Open a new PowerShell terminal.


Expected output:

```text

```

```powershell
python -m pip --version
```

If multiple Python versions are installed, ensure that Python 3.12 is used for the project environment.

## 3. Create and Activate a Python Virtual Environment

A virtual environment keeps the project's Python dependencies separate from globally installed packages.

Run the following command from the project root:

```powershell

```
or
```powershell
python -3.12 -m venv .venv
```

This creates a `.venv` directory in the project root.

## 8. Configure Ollama

MeetMind uses Ollama to generate AI-powered meeting summaries using the Qwen 2.5 3B language model.

MeetMind supports two configurations:

1. Remote Ollama API.
2. Local Ollama installation.

A local Ollama installation is not required when using a properly configured remote API.

### Step 1: Create the Environment File

In the root directory of the project, create a file named `.env`.

You can use the provided `.env.example` file as a template:

```powershell
Copy-Item .env.example .env
```

The `.env` file should be located alongside `requirements.txt` and `README.md`.

### Step 2: Configure a Remote Ollama API

If you have access to a remote Ollama API, enter its configuration in `.env`:

```env
OLLAMA_BASE_URL=https://your-server.com
OLLAMA_API_KEY=your_api_key
OLLAMA_MODEL=qwen2.5:3b
```

Replace the example URL and API key with your actual credentials.

The remote server must expose an Ollama-compatible `/api/generate` endpoint.

The application automatically uses the configured remote API when `OLLAMA_BASE_URL` is provided.

**No local Ollama installation is required in this configuration.**

The remote server must be accessible, support the expected API request format, and have the configured model available.

### Step 3: Configure Local Ollama (Alternative)

If you do not have access to a remote Ollama API, you can run Ollama locally.

Download and install Ollama from:

https://ollama.com/download

After installation, open a terminal and download the required model:

```powershell
ollama pull qwen2.5:3b
```

Create or update the `.env` file:

```env
OLLAMA_BASE_URL=
OLLAMA_API_KEY=
OLLAMA_MODEL=qwen2.5:3b
```

When the remote URL is empty, MeetMind automatically uses the local endpoint:

```text
http://localhost:11434/api/generate
```

Make sure the Ollama service is running before generating meeting summaries.

Verify the downloaded model:

```powershell
ollama list
```

You should find:

```text
qwen2.5:3b
```

You can test the model using:

```powershell
ollama run qwen2.5:3b
```

Enter a simple prompt:

```text
Summarize the importance of effective meeting documentation.
```

Exit the interactive session using:

```text
/bye
```

Ollama normally runs its local service automatically after installation. If the service is not running, start it using:

```powershell
ollama serve
```

### Environment Variables

| Variable | Description |
|---|---|
| `OLLAMA_BASE_URL` | Remote Ollama server URL. Leave empty to use local Ollama. |
| `OLLAMA_API_KEY` | Optional API key for remote authentication. |
| `OLLAMA_MODEL` | Ollama model used for meeting summarization. |

### Important Ollama Configuration Notes

- A remote API URL takes priority over the local Ollama endpoint.
- If no remote URL is configured, the application uses local Ollama.
- If a configured remote server is unavailable, summary generation returns a connection error. It does not automatically switch to local Ollama.
- The configured model must be available on the selected Ollama server.
- The API key is optional and is sent as a Bearer authentication header when configured.
- Never upload your actual `.env` file or expose API credentials on GitHub.
- The `.env` file is excluded from Git through `.gitignore`.

# Processing Pipeline

The application follows a multi-stage audio-processing pipeline.

## 1. Audio Preprocessing

FFmpeg processes the uploaded recording and prepares the audio for subsequent processing.

This stage handles audio conversion and preprocessing required by the downstream models.

## 2. Speaker Diarization

Pyannote Audio analyzes the recording and determines when different speakers are speaking.

The output contains speaker labels and their corresponding time intervals.

Example:

```text
SPEAKER_00: 0.00s - 5.20s
SPEAKER_01: 5.20s - 12.40s
```

## 3. Speech Transcription

Faster-Whisper converts spoken audio into text.

It produces recognized text along with segment timestamps.

## 4. Speaker Matching

SpeechBrain ECAPA generates speaker embeddings from audio segments.

The application compares embeddings using cosine similarity to associate segments with speaker identities.

The configured threshold determines whether a segment is sufficiently similar to an existing speaker profile.

## 5. Transcript and Diarization Merging

The transcription and diarization results are combined to generate a structured transcript.

The resulting transcript contains:

- Spoken text.
- Speaker labels.
- Start timestamps.
- End timestamps.

## 6. AI Summarization

The generated transcript is provided to the configured Qwen 2.5 3B language model through Ollama.

Ollama can be accessed using either a remote API or a locally running service, depending on the `.env` configuration.

The model generates a structured meeting summary.

## 7. PDF Generation

ReportLab is used to generate downloadable transcript and summary reports.

# Important Notes

1. **First-time model downloads:** The first execution may take longer because Faster-Whisper, Pyannote, and SpeechBrain may need to download their model files.

2. **Hugging Face authentication:** Access to gated Pyannote models requires an authenticated Hugging Face account with the necessary model permissions.

3. **Ollama configuration:** AI summarization requires either a configured remote Ollama API or a locally running Ollama instance. Local installation is not required when using a remote API.

4. **Remote API availability:** A configured remote Ollama server must be accessible and have the configured model available. If the remote server is unavailable, summary generation reports an error rather than automatically switching to local Ollama.

5. **GPU compatibility:** CUDA acceleration requires a compatible NVIDIA GPU, driver, and PyTorch installation. CPU execution may be slower.

6. **Virtual environment:** Always activate `.venv` before running backend commands or installing Python packages.

7. **Two terminal windows:** Keep the backend and frontend running in separate terminals during development.

8. **Generated files:** Audio recordings, intermediate files, transcripts, and PDF reports are generated locally and are not included in a fresh repository clone.

9. **Credentials:** Never upload Hugging Face access tokens, Ollama API keys, passwords, or other credentials to GitHub. Keep the actual `.env` file private.

10. **Meeting data:** Uploaded recordings and generated reports are stored locally by the application. Protect these files appropriately, particularly when they contain confidential meeting information.
